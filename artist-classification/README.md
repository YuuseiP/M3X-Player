# 歌手分类算法与首次确认

本阶段只生成离线分类草案，等待确认后再接入播放器。程序的唯一输入是现有报告 JSON；不会打开原始音乐目录，不修改音频、标签、文件名、现有报告或播放器代码。

## 查看产出

- `output/确认报告.md`：先看这个文件。包含统计、关键疑点、实际分类示例和需要确认的规则。
- `output/signature-review.md`：全部 1,262 种原始 ARTIST 字符串与分类结果逐项对照。
- `output/classification-report.md`：完整分类目录、每个条目的关联文件数、候选合并列表。
- `output/classification.json`：逐文件原始记录、身份关联和反向索引，供后续实现使用。
- `output/review.json`：所有署名的解析依据、路径、待确认项、候选别名及角色/CV 对应差异。

所有产出均为 `pending_user_confirmation`，没有表示用户已经批准。文件数、署名字符串数和身份条目数是不同口径；一个文件可进入多个分类，不能把各模式数量相加。

## 算法

1. 校验扫描记录数、路径唯一性及原生字段数组，逐曲完整保留原记录。曲目临时 ID 来自相对路径，供本阶段比对；软件接入时沿用软件现有歌曲 ID，不拿这个 ID 替换收藏、歌单及历史里的 ID。
2. 首先识别括号范围，在括号外按逗号、顿号或 `feat.` 拆分。斜杠、分号、`&` 只在两侧都能识别为角色、声优或已配置团体时拆分。无法确认的部分保留原文并进入待确认清单。
3. 解析明确的 `角色(CV:声优)`，将观察到的角色名与声优名分别建索引。无 CV 的括号只有在本快照中存在同一角色—声优对应证据时才解析。不会因为角色关系存在，就替无 CV 的另一首歌补声优。
4. 已配置团体按独立团体保留。明确的“团体(成员名单)”可生成团体及名单内的身份；仅有团名时不推断成员。团体配置和新推断的类型均属于本轮审核对象。
5. “双海亜美/真美”使用一条可见配置展开，不采用任意共享姓氏推断。每首歌每个身份只关联一次，合唱不复制歌曲。
6. 非 CV 括号不删除；不明确的创作者或商业署名保留在“其他署名（类型未定）”。`ARTIST` 里的名字不自动判定为主唱。
7. 首尾空白及 CV 结构标点可规整用于派生分类。姓名内部空格、NFKC 全半角及字形差异只提出别名候选，不自动合并。`approved_aliases` 按身份类型生效，初始为空。
8. 专辑艺术家独立索引，按首尾去空白后的完整值去重。不同专辑艺术家字段冲突时两个值都保留、标记待确认，不拿它填歌曲演唱者。`Various Artists` 等专辑署名保留在专辑维度，不生成真实人物。
9. 没有暴露标签的文件记录为“读取不可判定”，不等同于确认缺失。不从目录、标题或其他曲目猜歌手。

当前不做在线人物资料核查、不推断团体历史成员、不自动纠正疑似错标。角色/CV 关系来自快照，可能包含原标签错误，不能当作官方人物资料库。

## 重跑与检查

仅使用 Python 标准库，无新增依赖。在项目根目录执行：

```powershell
$env:PYTHONIOENCODING = 'utf-8'
$env:PYTHONDONTWRITEBYTECODE = '1'
python -m unittest discover -s 'artist-classification' -p 'test_*.py' -v
python 'artist-classification\classify_artists.py' '歌手问题汇报_2026-10-26\歌手标签扫描明细.json'
```

脚本只覆盖本目录 `output` 中的四个可再生成产物；`确认报告.md` 是本次运行结果的人工核对说明。调整算法和规则后应同步更新确认报告，避免引用旧统计。

程序会检查输入快照读取前后字节一致、所有原始记录保留、曲目无丢失或重复、正反索引一致，并回读输出 JSON 验证。测试另外覆盖 CV 标点、合唱分隔、括号嵌套、共享前缀简写、声优更替、错误对应、机构括号、无法读取标签、多值去重及重复运行一致性。
